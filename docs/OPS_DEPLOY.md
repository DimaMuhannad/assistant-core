# OPS_DEPLOY.md: Выкатка и смоук-проверка сервиса assistant-worker

## 1. Назначение

Настоящий документ определяет регламент выкатки и смоук-проверки сервиса `assistant-worker` (Python-демон персонального ассистента в репозитории assistant-core).

Процедура выполняется после фаз разработки, которые вносят изменения в рантайм (каталог `src/`).

Для выполнения выкатки и проверки используется скрипт `scripts/deploy.py`:
- написан с использованием исключительно стандартной библиотеки Python;
- запускается из рабочей директории `/opt/assistant-core`.

## 2. Правила

При проведении выкатки и смоук-проверки соблюдаются обязательные правила:

- **а) Рестарт сервиса:** перезапуск `assistant-worker` выполняется только по явному разрешению владельца. Claude передаёт флаг `--restart` только после ответа «да» владельца в интерактивном опросе в чате. Владелец также имеет право запустить скрипт самостоятельно.
- **б) Заморозка сервисов:** в Phase 1 и в фазах без изменений рантайма рестарт не нужен. Сервисы `assistant-worker` и `chat-app` заморожены.
- **в) Режим чтения по умолчанию:** без передачи флагов скрипт ничего не меняет в системе, а только читает данные.
- **г) Доступ к базе данных:** боевая БД открывается только при указании флага `--backup`.

## 3. Команды

Параметры командной строки скрипта `scripts/deploy.py`:

| Флаг | Что делает | Значение по умолчанию |
|---|---|---|
| `--backup` | Сделать резервную копию боевой БД (backup API, источник mode=ro) вне дерева git, права 0600 в каталоге 0700; без других флагов больше ничего не делает | отключено |
| `--backup-dir` | Каталог резервных копий, только с `--backup`; путь внутри любого репозитория (запись `.git` у пути или предка) отвергается до создания | `/var/backups/assistant-core` |
| `--restart` | Перезапустить assistant-worker, дождаться новой инвокации и polling, повторить смоук; только по разрешению владельца; при красном исходе откат лишь печатается | отключено |
| `--report` | Записать markdown-отчёт в PATH (каталог должен существовать, не внутри .git, не символическая ссылка, не FIFO и не каталог) | не задан |
| `--state-file` | Файл состояния смоука вне репозитория; путь по умолчанию в каталоге 0700, отказ при символической ссылке, чужом владельце или правах группы и остальных | `/var/lib/assistant-core/smoke-state.json` |
| `--await-help` | Ждать в журнале обработанное обновление после метки смоука (отправьте боту /help) | отключено |
| `--await-timeout` | Дедлайн для `--await-help` в секундах | `120` |
| `--confirm-help` | Записать ответ владельца на /help (ответ Claude получает опросом в чате) | не задан |

Примеры вызова:

1. **Read-only смоук:**
   ```bash
   python3 scripts/deploy.py
   ```
2. **Только резервная копия:**
   ```bash
   python3 scripts/deploy.py --backup
   ```
3. **Полный цикл выкатки:**
   ```bash
   python3 scripts/deploy.py --backup --restart --report /var/tmp/deploy-report.md
   ```
   После завершения автоматической части выполняются фазы без TTY (раздел 6).
4. **Фазы подтверждения бота:**
   ```bash
   python3 scripts/deploy.py --await-help
   python3 scripts/deploy.py --confirm-help yes
   ```

Коды возврата:
- `0` — успех;
- `1` — красный результат или сбой;
- `2` — отказ до начала действий (неверные флаги, грязное дерево git при `--restart`, недоступный путь отчёта, нет файла состояния).

Правила сочетания флагов:
- Флаги `--backup` и `--restart` нельзя сочетать с `--await-help` и `--confirm-help`.
- Флаг `--backup-dir` допустим только вместе с `--backup`.
- Флаги `--await-help` и `--confirm-help` взаимоисключающие.

## 4. Что проверяет смоук

Таблица проверок автоматической части смоука:

| Имя проверки | Что проверяет |
|---|---|
| `сервис active` | Состояние ActiveState сервиса |
| `журнал текущего запуска доступен` | Журнал берётся по InvocationID текущей инвокации, а не по времени |
| `в окне старта нет ERROR/CRITICAL/Traceback` | Отсутствие строк ERROR, CRITICAL и Traceback в окне старта |
| `polling бота запущен (запись в журнале)` | Наличие в журнале строки «Run polling for bot» |
| `планировщик: задачи зарегистрированы (N из M)` | Ожидаемые задачи берутся ast-разбором `src/main.py`, подтверждаются строками журнала «Added job» и «Scheduler started»; задачи под условием `if` показываются, но не краснят смоук |
| `getMe: токен бота жив` | Запрос getMe к Telegram, токен читается из `.env` только по ключу `TELEGRAM_BOT_TOKEN`, значение нигде не печатается |

Итог автоматической части: ЗЕЛЁНАЯ или КРАСНАЯ.

Ответ бота на `/help` автоматически не проверяется: он подтверждается отдельными фазами без TTY (раздел 6), итоговый вердикт смоука ЗЕЛЁНЫЙ только после них.

## 5. Окно ошибок старта

Окно старта сервиса: от начала инвокации до записи «Run polling for bot» плюс 60 секунд (константа STARTUP_TAIL_SECONDS).

Строки ERROR, CRITICAL и Traceback в этом окне делают смоук КРАСНЫМ.

Решение владельца 2026-10-09: критерий D-08 строгий, белого списка внешних ошибок нет. Для каждой ошибки печатается логгер и очищенное усечённое сообщение (до 160 символов).

Записи уровня WARNING только считаются по логгерам и вердикт не меняют.

Как решать про повтор при внешнем сбое:
- при сбоях внешних сервисов (сайт LMS, IMAP, `database is locked`, сеть) красный смоук законен;
- отчёт показывает логгер и сообщение сбоя;
- владелец решает, повторить ли выкатку или смоук;
- скрипт сам ничего не повторяет и не обходит.

## 6. Фазы без TTY

Процедура фаз без TTY (D-09) состоит из трёх шагов:

1. Запуск `python3 scripts/deploy.py` (сохраняет файл состояния, по умолчанию `/var/lib/assistant-core/smoke-state.json`, права файла 0600). Каталог `/var/lib/assistant-core` создаётся при первом запуске с правами 0700; существующий каталог с чужим владельцем или с правами группы и остальных даёт отказ с кодом 2 до любой команды. Запись атомарная: временный файл рядом и замена через `os.replace`, символическая ссылка на месте файла заменяется, а не открывается.
2. Владелец отправляет боту команду `/help`, затем `python3 scripts/deploy.py --await-help` ждёт в журнале строку «Update id=N is handled» после метки смоука (шаг опроса 5 секунд, дедлайн `--await-timeout`, по умолчанию 120 секунд).
3. Claude спрашивает владельца опросом в чате, пришёл ли ответ бота, и выполняет `python3 scripts/deploy.py --confirm-help yes` (или `no`).

Итог ЗЕЛЁНЫЙ достижим только при зелёной автоматической части, обработанном обновлении и ответе «да».

Перед фазами сверяется InvocationID: если сервис перезапускался после смоука, фаза отказывает и просит повторить автоматическую часть.

Файл состояния читается без следования по символической ссылке. Фаза отказывает с кодом 2, если файл состояния является символической ссылкой, принадлежит другому пользователю или доступен группе и остальным: подложенный файл не может подменить вердикт смоука (WR-08).

Ограничения:
- строка «Update id=N is handled» не содержит текста команды, засчитывается любое сообщение боту, поэтому ответ владельца авторитетен;
- скрипт не вызывает getUpdates и не использует сессию пользовательского клиента Telegram.

## 7. Резервная копия

Резервная копия базы данных (D-11) выполняется только по флагу `--backup`.

Правила создания резервной копии:
- копия делается через sqlite3 backup API, источник открывается в режиме `mode=ro`;
- каталог по умолчанию `/var/backups/assistant-core` (меняется `--backup-dir`) должен быть вне дерева git: отказ до создания каталога, если сам путь или любой существующий предок содержит запись `.git` (каталог или файл), в том числе другой репозиторий на хосте;
- несуществующий каталог создаётся с правами 0700, и права меняются только у каталога, созданного этим вызовом;
- существующий каталог принимается, только если он принадлежит текущему пользователю и не имеет прав группы и остальных; каталог с чужим владельцем или широкими правами отвергается (`BackupPathError`), его права не меняются, копия не создаётся;
- права файла копии 0600;
- имя файла `assistant-<UTC yyyymmdd-HHMMSS>.db`; существующий файл не перезаписывается;
- на копии выполняется `PRAGMA integrity_check`; при сбое копия удаляется;
- копия самодостаточна (без WAL и sidecar-файлов);
- скрипт печатает путь и размер, содержимое не печатается.

ОБЯЗАННОСТЬ Phase 3: вызвать выкатку с `--backup` ПЕРЕД применением миграции `0003`. В Phase 1 живая копия не делалась; первый живой `--backup` произойдёт в Phase 3 с разрешения владельца.

## 8. Рестарт

Порядок действий при передаче флага `--restart`:

1. Дерево git должно быть чистым вне `.planning/`, иначе скрипт печатает список ПУТЕЙ (без содержимого), возвращает 2 и не вызывает systemctl.
2. Определяется HEAD и его родитель.
3. При `--backup` делается копия (сбой копии останавливает выкатку до рестарта).
4. Запоминается прежняя инвокация.
5. Выполняется `systemctl restart assistant-worker` с таймаутом 300 секунд (останов может длиться до 90 секунд до SIGKILL).
6. Ожидание до 300 секунд новой инвокации в состоянии active и строки «Run polling for bot» (шаг 5 секунд). Если сервис не вернулся за 300 секунд, результат КРАСНЫЙ и смоук не запускается.
7. Пауза 60 секунд, чтобы окно ошибок старта успело заполниться.
8. Тот же смоук, что и без флага; при зелёной автоматической части печатается инструкция фаз без TTY.

Каталог состояния по умолчанию проверяется ДО шага 1: небезопасный `/var/lib/assistant-core` (чужой владелец или широкие права) даёт отказ с кодом 2 и не вызывает systemctl.

## 9. Откат

Автоотката нет (D-12).

При красном исходе после рестарта скрипт останавливается и печатает «ОТЧЁТ О СБОЕ ВЫКАТКИ»:
- описание того, что упало;
- пронумерованные команды отката.

Если выкатка шла с `--backup`:
1. `git revert --no-edit <HEAD>` (откат кода новым коммитом; при нескольких коммитах владелец указывает диапазон сам);
2. `systemctl stop assistant-worker`;
3. `cp -p <копия> data/assistant.db` (путь копии и БД скрипт подставляет сам);
4. `rm -f` для sidecar-файлов WAL и SHM прежней БД, если остались;
5. `systemctl start assistant-worker`.

Если выкатка шла без `--backup`: `git revert --no-edit <HEAD>` и `systemctl restart assistant-worker`. Откат БД при этом невозможен: резервной копии не было.

Предупреждение: восстановление из копии затрёт данные, появившиеся после выкатки.

Команды ТОЛЬКО печатаются; скрипт не исполняет ни revert, ни checkout, ни cp, ни повторный restart; откат требует нового разрешения владельца.

## 10. Отчёт

Запись отчёта (D-13) управляется флагом `--report PATH`:

- создаётся markdown-файл с датой UTC, коммитом HEAD, InvocationID, таблицей проверок, ошибками окна старта, счётчиками WARNING по логгерам, подтверждением бота и итогом;
- каталог отчёта должен существовать, путь внутри `.git` отвергается;
- путь отчёта, который является символической ссылкой, каталогом или существующим файлом, не являющимся обычным файлом (например FIFO), отвергается с кодом 2 до любой команды;
- запись атомарная: временный файл рядом с целью, затем замена через `os.replace`; права файла 0600;
- отчёт пишется и при красном исходе;
- Claude включает отчёт в VERIFICATION.md фазы;
- в отчёт не попадают секреты, токены, e-mail и содержимое сообщений.

## 11. Чего смоук не делает

Смоук не выполняет следующие действия:

- не пишет в БД и не открывает её (кроме `--backup`);
- не импортирует `src`;
- не вызывает getUpdates;
- не открывает сессии пользовательского клиента Telegram;
- не перезапускает и не останавливает сервис без `--restart`.

## 12. Известные ограничения

Известные ограничения смоука и процедуры выкатки:

- **Ротация журнала:** при ротации записей инвокации нет, смоук красный с подсказкой;
- **Обработка обновлений бота:** любое сообщение боту засчитывается в журнале как обработанное обновление;
- **Файлы SQLite при чтении:** чтение боевой БД для копии в режиме `mode=ro` может создать sidecar-файлы SQLite (`-wal`, `-shm`), если их не было;
- **Строгость окна ошибок:** окно ошибок строгое, внешний сбой в окне старта краснит смоук.
