### Phase 999.2: Цепочка web-HITL → Telegram (BACKLOG)

**Deferred at:** 2026-10-18, решение владельца при /gsd-discuss-phase 5: веб-интерфейс (chat-app) на этом этапе не нужен, работа идёт только с чат-ассистентом в Telegram.
**Код-разведка (2026-10-18), для будущего планирования:** `send_web_hitl_card` и обработчики `hitl:confirm/reject` в `src/notifier/bot_handler.py` есть, поллера нет; chat-app создаёт запись с TTL 10 мин, а веб опрашивает статус только 60 с (`pollConfirmation` в `backend/app/static/index.html`); статус `confirmed` ставится до выполнения обработчика, поэтому сбой удаления веб не видит; проверить, что chat-app и демон пишут в одну БД (`SQLITE_DB_PATH` chat-app по умолчанию `./data/assistant.db` относительно `/opt/chat-app/backend`).

**Goal**: Необратимое действие, начатое в web-интерфейсе, не выполняется, пока владелец не подтвердит его карточкой в Telegram. Карточка доставляется автоматически, а web видит честный статус вместо таймаута.
**Depends on**: Phase 3 и процедура OPS-01 из Phase 1
**Requirements**: HIT-02, HIT-03, HIT-04
**Success Criteria** (what must be TRUE):
  1. Поллер `ConfirmationChannel.WEB` в демоне находит новое web-подтверждение и вызывает `send_web_hitl_card` (`src/notifier/bot_handler.py`): карточка «Да / Отмена» приходит владельцу в Telegram с проверкой `allowed_user_id` (HIT-02).
  2. Сквозной сценарий «web DELETE → 409 и запись в `pending_confirmations` → карточка в Telegram → подтверждение → `resume_action` выполняет удаление» проходит интеграционным тестом на временной БД, а отмена ничего не удаляет (HIT-03).
  3. Подтвердить действие можно только из авторизованного канала (Telegram владельца), а web-интерфейс видит статус «ожидает / подтверждено / отклонено» вместо таймаута в 60 с (HIT-04).
  4. VERIFICATION.md доказывает достижимость из рантайма: поллер зарегистрирован в `src/main.py` и виден в журнале старта, а карточка доходит до бота без ручного вызова функции. Рестарт `assistant-worker` выполнен только после разрешения владельца, смоук-проверка OPS-01 пройдена.

**Plans**: TBD
**UI hint**: no
**Заметки для планирования**: статус «ожидает / подтверждено / отклонено» на стороне web (HIT-04) может потребовать мелкой правки chat-app. Она делается только через `/gsd-quick` в его репозитории, pytest chat-app остаётся зелёным.

### Phase 999.22: Коннекторы и брифинги из диалога (BACKLOG)

**Deferred at:** 2026-10-19 — v3.0 закрыта как есть (решение владельца); бывшая Phase 8 v3.0, порядок и ценность пересмотреть после новой вехи (todo review-phases-6-8-after-5-2.md)

**Goal**: Пользователь управляет подключениями сервисов и расписанием брифингов обычными фразами в чате, без правки конфигурации и без рестарта демона.
**Depends on**: Phase 7
**Requirements**: ONB-02, ONB-03
**Success Criteria** (what must be TRUE):
  1. Пользователь пишет «подключи почту»: параметры запрашиваются по шагам, выполняется `health_check`, и коннектор активируется и регистрируется в `connector_bindings` без рестарта. При неуспешном `health_check` коннектор не активируется, и пользователь видит понятную причину по-русски (ONB-02).
  2. Токены и пароли не попадают в LLM-промпты и логи (проверяется ловушкой на промпте и перехватом логов). Диалог подключения почты показывает предупреждение PRIV-01 из Phase 2 (ONB-02).
  3. Пользователь пишет «отключи LMS»: отключение требует HITL-карточки, подтверждение убирает привязку, отмена ничего не меняет. После подключения и отключения меню команд бота обновляется (UXQ-01) (ONB-02).
  4. Пользователь меняет в диалоге время и состав блоков утреннего брифинга (погода, почта, расписание, табель) и вечернего дайджеста. Изменения сохраняются в персоне или БД, и планировщик применяет их без рестарта (ONB-03).
  5. VERIFICATION.md доказывает достижимость из рантайма: фразы доходят из бота через `intent_router`/`SecretaryDialogEngine`, а смена времени брифинга видна в списке задач планировщика. Рестарт `assistant-worker` выполнен только после разрешения владельца, смоук-проверка OPS-01 пройдена.
