# Проактивная картина владельца

## Проблема владельца

Ассистенту не хватает автономии и проактивности: он не анализирует картину проблем владельца
по всем собранным данным. Владелец хочет запустить ассистента для себя, а не решать
«подкапотные» задачи.

## Решения владельца (2026-10-19)

1. **Охват:** все четыре класса проблем:
   - сроки и долги (письма без ответа, непроверенные работы LMS, просроченные задачи);
   - конфликты времени и нагрузки (пересечения расписания и встреч, перегруз, недобор табеля);
   - важное, утонувшее в потоке (просьбы и обещания в Telegram и почте);
   - системные закономерности (тренды за недели).
2. **Автономия:** «сообщить + готовое действие». Карточка «проблема → предложение» с уже
   подготовленным действием (например, черновик ответа) и кнопками «Отправить / Изменить / Отложить».
   Всё внешнее — через HITL.
3. **Ритм:** срочное (срок сегодня или завтра, конфликт в ближайшие часы) — сразу, с дневным
   лимитом и тихими часами; остальное — блоком «Картина дня» в утреннем брифинге; тренды —
   в недельном обзоре.
4. **NDA:** владелец отказался от скрытия данных на этом этапе («я сам решу, какие данные давать»).
   Новый анализ не проектируется под NDA. Удаление существующих механизмов NDA — бэклог,
   не первоочередная задача (Phase 999.17). Gap ISO-05 (999.4) больше не приоритет.

5. **Углублённый сбор из мессенджеров (добавлено владельцем 2026-10-19, входит в 5.2):**
   ассистент опрашивает владельца, за какими чатами и группами следить, а какие игнорировать;
   следит за появлением новых чатов (и спрашивает о них); индексирует выбранные чаты.
   В 5.2 — Telegram (личные чаты, группы, каналы). ВКонтакте и MAX нужны позже —
   бэклог 999.18 с проверкой доступного API.
   Сейчас: сбор только по вручную внесённым `monitored_sources` (`src/main.py:170`),
   `list_dialogs` (`src/collector/tg_collector.py:59`) не используется для выбора,
   списка игнорирования и обнаружения новых чатов нет.

6. **Проекты из диалога (добавлено владельцем 2026-10-19, Phase 05.3):** владелец рассказывает
   о себе, новых задачах и проектах; проекты разворачиваются в Notion в стиле проектной
   деятельности, подключаются репозитории, идёт мониторинг и напоминания, какой проект требует
   внимания. Сигнал «проект требует внимания» — правило в движке проблем 05.2, остальное — 05.3.
   Сейчас: Notion-клиент умеет задачи, «ожидающие», дневник и журнал активности проекта;
   таблица `projects` наполняется захардкоженным засевом (`src/storage/db.py:1325`); диалогового
   ввода проектов и подключения репозитория из чата нет.

7. **Пересмотр карточек и UI (добавлено владельцем 2026-10-19, Phase 05.1 — первой):** пересмотреть
   все существующие карточки и UI-элементы, чтобы снизить шум и дать быстрый анализ состояния
   почты, проектов, задач, долгов и недоработанного времени по табелю. Аудит — по коду и вживую
   с владельцем. Фазы перенумерованы: проактивная картина — 05.2, проекты из диалога — 05.3.

8. **Новая веха (решение владельца 2026-10-19):** вместо вставки фаз 05.1–05.3 в v3.0 —
   закрыть v3.0 и начать веху «Автономный секретарь» с новыми требованиями; фазы 6–8 v3.0
   и вставленные 05.1–05.3 переносятся во входные данные новой вехи или в бэклог.

## Оценка архитектуры против практики (2026-10-19)

Вердикт: полный рефакторинг не нужен; нужен точечный фундамент бэкенда первой фазой новой вехи.

Соответствует практике (остаётся): сбор данных, SQLite + миграции, порты коннекторов,
composition root, контракты импортов; `ConfirmationStore` + `resume_action` (долговременные
ожидающие действия — основа паттерна «ящик предложений»); маршрутизация моделей.

Расхождения (проверено по коду 2026-10-19):
1. Нет единого канала доставки проактивных сообщений: ~10 методов `send_*` и прямые вызовы
   в `src/main.py`. Без него невозможны лимит в день, группировка в сводку, «Не важно», тихие часы.
2. У `SecretaryDialogEngine` 4 инструмента (`create_calendar_event`, `create_reminder`,
   `draft_email_reply`, `search_emails`); остальное — 18 жёстких действий `intent_router`
   и команды. Задачи, проекты, табель, LMS, Notion в диалоге недоступны.
3. FTS5 есть только для методички (`methodist_chunks_fts`), не для почты и Telegram.
4. Нет сводного профиля «я и мои проекты», есть отдельные `memory_facts`.
5. `EventBus` (`src/core/events/bus.py`) не используется в рантайме.
6. `src/notifier/bot_handler.py` — 3432 строки; дробить постепенно, не отдельной переделкой.

Предложенный порядок новой вехи: (1) фундамент — единый канал доставки, хранилище сигналов
и их состояний, шина событий от сборщиков, расширение инструментов диалога; (2) пересмотр
карточек и сводка состояния; (3) проактивная картина и углублённый Telegram; (4) проекты из
диалога в Notion, профиль, поиск FTS5.

## Проверенная практика (поиск 2026-10-19)

Исследование выполнял Claude напрямую (не субагент); источники — в основном блоги вендоров
и препринты, единого стандарта нет.

- Admit: паттерн ambient agents / Agent Inbox — три вида сигналов «уведомить / спросить /
  на проверку», единая очередь, долговременное хранение ожидающих действий
  (https://www.langchain.com/blog/introducing-ambient-agents).
- Admit: темы в личном чате с ботом — Bot API 9.3, создание ботом — 9.4
  (https://core.telegram.org/bots/api-changelog).
- Unresolved (одиночный отчёт, не подтверждён): после Bot API 10.0 отправка в тему личного
  чата возвращает «message thread not found» (https://github.com/tdlib/telegram-bot-api/issues/847).
  Проверить на живом боте до использования.
- Admit (как консенсус): слоистая память — профиль + эпизоды + рабочий контекст
  (https://arxiv.org/pdf/2601.02163, https://arxiv.org/pdf/2604.04853).
- Unresolved (непроверяемо, мнение автора): дневной лимит 3–5 проактивных сообщений и
  отбор по «ценность против цены отвлечения»
  (https://tianpan.co/blog/2026/05/13/background-agents-notification-budget-attention-economy).
- Unresolved (непроверяемо, мнение): пользователям нужен выключатель проактивности
  (https://aispaces.substack.com/p/ai-ux-is-breaking).

Идеи для требований новой вехи: живое редактируемое сообщение-сводка; «Отменить» вместо
«Подтвердить» для обратимого; «Не важно» на карточке с подстройкой порогов; лимит проактивных
сообщений в день и выключатель; темы по областям (после проверки); единый ящик предложений;
отслеживание обещаний владельца; «Пока вас не было»; профиль «я и мои проекты»; вопросы по
своим данным; еженедельный обзор.

## Что уже есть в коде (обзор 2026-10-19)

- Данные собираются почти все: таблицы `email_messages`, `email_threads`, `email_drafts`, `tasks`,
  `reminders`, `action_items` (из Telegram), `lms_submissions`, `timesheet_records`,
  `content_snapshots` (расписание), `calendar_sync_records`, `memory_facts`.
- `generate_morning_brief` / `generate_evening_digest` (`src/brain/summarizer.py`) перечисляют
  источники по отдельности: пары, пункты действий, письма, темп табеля.
- Срочный алерт есть только для пунктов действий Telegram с приоритетом ≥ 3
  (`src/main.py:188-194`, `send_action_items_alert`).
- `send_connector_health_alert` существует, но не вызывается (gap UXQ-04, 999.11).

## Чего нет

- Слоя, который сопоставляет источники и детерминированно находит проблемы.
- Состояния найденных проблем: показано / отложено / решено, без повторов.
- Карточек с подготовленным действием.
- Недельных трендов.

## Вывод

Новые источники не нужны: нужен слой анализа поверх собранных данных. Объём — одна фаза
(5.2), возможно в два шага: (1) поиск проблем и блок «Картина дня»; (2) карточки с действием,
срочные алерты, тренды. После 5.2 пересмотреть фазы 6–8.
