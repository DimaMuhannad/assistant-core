# Фаза 4: runbook исполнения для агента agy

Решение владельца (2026-10-11): agy запускается владельцем в корне `/opt/assistant-core` без участия Claude и без обёртки `agy_task.sh`, с теми же правами доступа, что у Claude. У agy нет команд GSD, скиллов и инструмента Agent, поэтому весь порядок работы описан здесь. Агент не видит историю чата, всё нужное лежит в файлах.

## 0. Роль агента

Agy сам читает, правит, запускает тесты и `python3 scripts/gate.py`, делает атомарные коммиты прямо в `main` (разрешено CLAUDE.md, без worktree) и пишет `04-NN-SUMMARY.md` после каждого плана. Рабочие каталоги: `/opt/assistant-core` и `/opt/assistant-shared` (план 04-02).

Отсутствие изоляции увеличивает цену ошибки, поэтому запреты из раздела 5 действуют жёстко. Агент работает один план за раз и останавливается на каждом пункте «СТОП».

## 1. Что прочитать агенту перед каждым планом (в таком порядке)

1. `/opt/assistant-core/CLAUDE.md` и `/opt/assistant-core/.claude/CLAUDE.md`: стек, NDA air-gap, HITL, запреты.
2. `.planning/phases/04-tsepochka-git-otsenka-hitl-notion/04-CONTEXT.md`: решения D-01..D-14, они не пересматриваются.
3. `04-PATTERNS.md`: аналоги в коде и фрагменты, по которым пишется новый код.
4. `04-VALIDATION.md`: какие тесты и команды относятся к каким требованиям.
5. Нужный `04-NN-PLAN.md` целиком, включая `<threat_model>` и «Artifacts this phase produces».
6. Файлы из `<read_first>` каждой задачи, до любой правки.

Копия клетки содержит только закоммиченные файлы. Если `.planning/` в клетке нет, Claude вставляет тексты пунктов 2–5 прямо в задачу.

## 2. Правила исполнения плана

- Задачи идут по порядку. Задача считается сделанной, когда выполнены все пункты её `<acceptance_criteria>` по тексту кода. Команды из `<verify>` запускает Claude, и красная команда отправляет задачу на доработку.
- Править только файлы из `files_modified` плана. Любой другой файл: остановиться и написать об этом в отчёте.
- В `<action>` указаны точные идентификаторы. Их нельзя переименовывать и «улучшать».
- Комментарии и тексты для пользователя: по-русски. Логи: `logger.warning("... %s", x)`, без f-строк, без `print`.
- Новые зависимости запрещены. Файлы `data/assistant.db`, `.env`, `credentials.json`, `token.json` не открываются.
- Допуск рабочего пространства (`git_chain_workspaces`) проверяется до любого git, LLM или Notion. Это инвариант фазы, сомнение трактуется как отказ.
- Формат ответа агента: список изменённых файлов, по одной строке на пункт acceptance_criteria («выполнено / не выполнено + файл:строка») и список отклонений от плана. Лимит: 60 строк.

## 3. Порядок планов и «независимые исполнители»

В agy нет субагентов, поэтому независимость = **новая сессия agy без общего контекста** (владелец открывает её сам). Контекст между сессиями передаётся только файлами: SUMMARY.md и git.

|---|---|---|---|
| 1 | 04-01 трассирующий срез | нет | Самый крупный. После него полный `gate.py`: на нём стоит остальное. |
| 1 | 04-02 assistant-shared | с 04-03, 04-04 | Коммит там: `git -C /opt/assistant-shared`. Каталог миграций не трогать. |
| 1 | 04-03 персона и конфиг | с 04-02, 04-04 | |
| 1 | 04-04 клиент Notion | с 04-02, 04-03 | |
| 2 | 04-05 допуск и git-провайдер | с 04-06 | Логика безопасности. |
| 2 | 04-06 LLM-сводка | с 04-05 | |
| 3 | 04-07 идемпотентные карточки | нет | |
| 4 | 04-08 подключение в `main()` | с 04-09 | |
| 4 | 04-09 команда `/git` | с 04-08 | `bot_handler.py` общий с 04-01: только после коммита 04-01. |
| 5 | 04-10 ловушки и сквозные тесты | нет | Исполнять в **новой сессии**: автор ловушек не должен быть автором кода волн 1–4. |

Параллельные планы одной волны безопасно вести в разных сессиях только при отсутствии общих файлов в `files_modified` (проверено для 02/03/04, 05/06, 08/09). Одновременные `git commit` из двух сессий недопустимы: коммитить по очереди, перед коммитом `git status`.

Независимые проверки (каждая в **новой сессии**, режим только чтения, результат записать в файл фазы):
- **После волны 2:** ревью допуска. Найти путь, по которому NDA-пространство или неизвестный `clearance` достигает git, LLM или Notion. Итог в `04-REVIEW-AIRGAP.md`.
- **После волны 5:** проверка достижимости из рантайма: `git_progress_job` в `add_job`, `Command("git")`, колбэки `ntn:*`, создание оценщика до `EmailBotHandler`. Итог в `04-REVIEW-REACHABILITY.md`.
- **Конец фазы:** `04-VERIFICATION.md` пишет не автор кода, а новая сессия по критериям фазы из `ROADMAP.md`.

## 4. Цикл на каждый план

1. Прочитать материалы раздела 1.
2. Выполнить задачи по порядку, после каждой запустить её `<verify>` команды.
3. Красный тест: исправить, не ослабляя тест. Нельзя добавлять skip, xfail, deselect.
4. После плана: `.venv/bin/pytest` по затронутым тестам, после волны `python3 scripts/gate.py` (код 0 = ЗЕЛЁНЫЙ).
5. Атомарный коммит на задачу (`feat(04-NN): ...` / `test(04-NN): ...`), pre-commit хук не обходить (единственное исключение: план 04-11 с согласием владельца).
6. Написать `04-NN-SUMMARY.md` в каталоге фазы и закоммитить.

## 5. Остановки и запреты

- Планы 04-11 и 04-13 имеют `autonomous: false`: стоп до ответа владельца.
- `assistant-worker.service` не перезапускается без явного «да», только через `python3 scripts/deploy.py --backup --restart`.
- Не вставлять секреты и содержимое NDA-документов ни в код, ни в коммиты, ни в SUMMARY. Запускать `.venv/bin/python3 scripts/security_shield.py` при сомнениях.
- Тесты используют только `tmp_path`-БД. Боевую `data/assistant.db` не открывать даже на чтение, `tests/live_db_guard.py` не отключать.
- Не править `scripts/gate.py`, `.githooks/`, `.importlinter`, `scripts/security_shield.py`: проверки только ужесточаются.
- Цель 100% прохождения тестов: пропуски, xfail и deselected делают гейт красным.
- Если план требует решения, которого нет в CONTEXT/RESEARCH, агент останавливается и пишет вопрос в отчёте. Выдумывать нельзя.
