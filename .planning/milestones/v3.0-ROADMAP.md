# Roadmap: Assistant Core

## Milestones

- 🚧 **v3.0 Стабилизация платформы и онбординг** - Phases 1-5 (in progress)

## Overview

Цикл v2.0 «Универсальная платформа» закрыт с оговоркой: у фаз 4–9 нет VERIFICATION.md, две сквозные цепочки (Git → Notion и web-HITL → Telegram) оказались «сиротами», недостижимыми из рантайма, а часть находок ревью осталась без исправлений. Цикл v3.0 сначала стабилизирует платформу, затем делает один шаг к универсальности. Порядок фаз выбран владельцем (вариант A): собственный гейт качества, затем безопасность и приватность, владение схемой БД, две сквозные цепочки в рантайме, ретро-верификация v2.0, быстрые действия по времени суток и, наконец, онбординг. Сначала строится инструмент проверки, потом закрываются риски безопасности и целостности данных, и только после этого добавляются функции. Главный урок v2.0 заложен в каждую фазу, меняющую рантайм: функция считается готовой, только когда VERIFICATION.md доказывает её достижимость из `src/main.py` (планировщик) или команды бота, а юнит-теста для этого недостаточно.

## Сквозные ограничения цикла

Действуют для всех фаз и не повторяются в каждой из них.

- **Боевая БД**: `/opt/assistant-core/data/assistant.db` не открывается и не меняется при разработке и тестах. Миграции проверяются на копии во временном каталоге или на временной БД.
- **Сервисы заморожены**: `assistant-worker.service` и `chat-app.service` не трогаются. Рестарт `assistant-worker` выполняется только после фазы с изменениями рантайма, по явному разрешению владельца, со смоук-проверкой OPS-01 (процедура создаётся в Phase 1).
- **chat-app**: правки только мелкой задачей `/gsd-quick` в репозитории chat-app. Его pytest остаётся зелёным.
- **Гейт всегда зелёный**: 100% тестов проходят; skip, xfail и deselected делают гейт красным.
- **Безопасность только ужесточается**: fail-closed; содержимое `restricted_nda` не уходит во внешнюю LLM; любое необратимое действие требует HITL.
- **Для пользователя всё по-русски**: сообщения бота, карточки и предупреждения.

### Phase Details

### Phase 1: Собственный гейт качества assistant-core

**Goal**: Владелец проверяет assistant-core и assistant-shared одной командой в собственном репозитории, не завися от общего `gate.py` chat-app, и получает по-русски однозначный итог «ЗЕЛЁНЫЙ» или «КРАСНЫЙ». Описана и автоматизирована процедура выкатки, которой пользуются все последующие фазы.
**Depends on**: Nothing (first phase)
**Requirements**: GATE-01, GATE-02, GATE-03, GATE-04, GATE-05, OPS-01
**Success Criteria** (what must be TRUE):
  1. Владелец запускает `python3 scripts/gate.py` в `/opt/assistant-core` и видит по-русски таблицу «проверка → ✓/✗» и «ИТОГ: ЗЕЛЁНЫЙ» (rc 0) на чистом дереве. Намеренно сломанный тест, skip, xfail, xpass, deselected или ноль собранных тестов дают «ИТОГ: КРАСНЫЙ» (rc ≠ 0), и гейт показывает результаты всех проверок, не обрываясь на первой ошибке (GATE-01).
  2. Тесты assistant-core не могут открыть боевую БД `data/assistant.db`: тест доказывает, что `load_dotenv(..., override=True)` из `src/config.py` не перебивает изолированный путь, а гейт сверяет SHA-256 боевой БД до и после прогона и печатает совпадение (GATE-02).
  3. У `/opt/assistant-shared` есть собственные pytest-тесты (мигратор, HITL-примитив, библиотека безопасности) и воспроизводимо установленный pre-commit hook, который блокирует синтетический секрет. Гейт показывает эти тесты отдельной строкой (GATE-03).
  4. Гейт не слабее общего `/opt/chat-app/scripts/gate.py` по части assistant-core: сохранены проверка дрейфа `tests/synthetic_persona.py` и `tests/persona_tokens.py` с копиями chat-app (только чтение) и замороженный список ложных срабатываний shield (записи только удаляются). Пробный прогон `agy_cross_ai.sh --repo /opt/assistant-core` и правила `CLAUDE.md` используют новый гейт и дают ЗЕЛЁНЫЙ (GATE-04, GATE-05).
  5. Процедура выкатки описана и автоматизирована скриптом: рестарт `assistant-worker.service` только по явному разрешению владельца, затем смоук-проверка (сервис active, в журнале старта нет ошибок, планировщик зарегистрировал задачи, бот отвечает на команду). Смоук-проверка не пишет в боевую БД, её read-only часть запускается на текущем сервисе без рестарта, и результат записан в VERIFICATION.md (OPS-01).

### Phase 2: Безопасность, приватность и находки ревью

**Goal**: NDA-режим и аудит безопасности определяются данными рабочих пространств и одинаково работают в web и CLI, текстовая команда «очисти диалог» не стирает историю необратимо без защиты, а пользователь заранее предупреждён, что почта обрабатывается внешними ИИ-сервисами.
**Depends on**: Phase 1
**Requirements**: SECF-01, SECF-02, SAFE-01, PRIV-01
**Success Criteria** (what must be TRUE):
  1. CLI-аудит определяет NDA-режим по данным `workspaces` (`clearance`, `forbidden_remote_substrings`). В `assistant_shared/security` нет подстроки пути «tydex» и литерала личного аккаунта (проверяется тестом), а тест паритета NDA не читает литерал из исходника (SECF-01).
  2. Web- и CLI-аудит используют общую функцию сканирования файла, web-аудит проверяет `forbidden_keywords` рабочего пространства, и на общем наборе синтетических фикстур (включая многострочные) оба пути дают одинаковый результат (SECF-02).
  3. Владелец пишет боту «очисти диалог» и не теряет историю без защиты: решение (HITL-карточка или обратимый архив с командой отмены) принято и записано, а поведение закреплено тестом (SAFE-01).
  4. При подключении почты и в справке бота (`/help`) пользователь видит предупреждение по-русски: содержимое писем обрабатывается внешними ИИ-сервисами (Gemini и др.), разработчик не отвечает за утечку секретов и личной информации. Текст берётся из данных персоны или интерфейса, а не из хардкода (PRIV-01).
  5. VERIFICATION.md показывает достижимость из рантайма: предупреждение выводится живой командой `/help` и точкой подключения почты, новое поведение «очисти диалог» воспроизводится текстовым сообщением боту, аудит запускается через `scripts/security_shield.py`. Security-логика только ужесточена (fail-closed), гейт ЗЕЛЁНЫЙ, рестарт `assistant-worker` выполнен только после разрешения владельца и смоук-проверка OPS-01 пройдена.

### Phase 3: Владение схемой БД

**Goal**: Схема БД принадлежит только миграциям `/opt/assistant-shared`, а тесты и боевой запуск используют один и тот же неблокирующий путь миграций. Это закрывает расщепление владения схемой между репозиториями.
**Depends on**: Phase 2 (порядок владельца; по существу нужны гейт и тесты assistant-shared из Phase 1)
**Requirements**: DAT-01, SCH-01, SCH-02
**Success Criteria** (what must be TRUE):
  1. Таблицы `bot_command_settings`, `bot_custom_aliases`, `dialog_feedback_log` создаются миграцией `0003_*.sql` в `/opt/assistant-shared`, а в `src/storage/db.py` нет инлайн-`CREATE TABLE` ни в одной из двух веток (проверяется тестом) (DAT-01).
  2. На копии боевой БД, сделанной во временный каталог при неизменном хеше оригинала, миграция применяется без изменения существующих данных (DAT-01).
  3. Ветки `:memory:` и файловой БД используют один путь миграций, ни одна не блокирует event loop, а тест паритета подтверждает совпадение схемы `:memory:`, файловой БД и миграций `assistant-shared` (SCH-01).
  4. chat-app получает таблицы `0003` через общий мигратор и не создаёт их сам, его pytest остаётся зелёным. Любая правка chat-app делается только через `/gsd-quick` (SCH-02).
  5. VERIFICATION.md показывает достижимость из рантайма: старт демона (`src/main.py` → `Database.init_db`) на временной БД применяет `0003`, а функции на этих таблицах (алиасы и скрытие команд бота, обратная связь 👍/👎) работают на мигрированной схеме. Боевая БД мигрирует сама только при рестарте, разрешённом владельцем, по процедуре OPS-01 с резервной копией как шагом процедуры.

### Phase 4: Цепочка Git → оценка → HITL → Notion

**Goal**: Владелец получает по-русски оценку хода проектов по git-репозиториям своих рабочих пространств и вносит её в Notion только после подтверждения в Telegram. Цепочка достижима из планировщика и из команды бота, а пространства `restricted_nda` исключены из неё полностью.
**Depends on**: Phase 3 (стабильная схема), Phase 2 (fail-closed NDA-логика до включения цепочки)
**Requirements**: GIT-01, GIT-02, GIT-03, GIT-04, NTN-01, NTN-02
**Success Criteria** (what must be TRUE):
  1. Репозитории подключаются только данными рабочего пространства (`git: host, account, ssh_alias, remote`) через `default_git_source_provider` и `SshGitProvider` (только чтение по SSH, scope `git.read`). Пространства без remote или каталога пропускаются, и владелец видит их статус в рантайме (GIT-01, GIT-02).
  2. `GitProgressEvaluator` создаётся в планировщике `src/main.py` (периодичность — данные персоны) и по команде бота, а владелец получает по-русски оценку хода проекта для public- и internal-репозиториев (GIT-03).
  3. Пространства `restricted_nda`, а также пространства с неопределённым допуском (fail-closed), исключены из цепочки: нет обращений к git, LLM и Notion, нет оценки и карточки; в ответе команды одна строка «NDA: исключено из оценки». Это доказано ловушками LLM-, git- и Notion-клиентов на рантайм-пути, а не на отдельном юните (GIT-04).
  4. Обработчик `notion_project_sync` зарегистрирован в рантайме, связь «пространство → проект Notion» берётся из персоны.
